# Analyse des fichiers et premières simulations

Date : 23 octobre 2026. Aucun original reçu n'a été modifié. Les empreintes SHA-256 ont été comparées avant et après les essais.

## 1. Couple PID reçu

Sources : `scenari0045.csv` (entrée), `Test_PID_P_AS_scenari0045.csv` (report).

- 1001 lignes de données chacun, séparateur virgule.
- 9 colonnes pour le scénario, 18 pour le report. Les neuf colonnes communes sont identiques ligne à ligne.
- `index` de 0 à 20000, pas constant 20, aucun doublon ni retour arrière. Unité et origine non indiquées dans les CSV, à confirmer avant conversion.
- Le scénario possède une marque BOM UTF-8, prise en charge par le lecteur.
- `VAR_INPUT1` passe de 0 à 10 à l'index 1000.
- `output` passe alors de 0 à 15 et continue à varier. `pv` commence à varier à l'index 1500.
- Aucune cellule vide ni ligne de longueur incorrecte détectée dans ce couple.

Ce cas vérifie la lecture de signaux variables et de types numériques/booléens. Il ne valide pas la justesse du modèle PID, ni une synchronisation entre horloges différentes.

## 2. Simulation de redondance

Sources : `Redundancy10(1).py`, `graphical_report10.py`, `generate_report10.py`.

Deux exécutions non modifiées ont réussi. Les deux CSV diffèrent, conformément aux phases et jitters aléatoires. Les phases de chaque exécution sont archivées dans `resultats_analyse.json`. Le message « deterministic log » du script ne signifie pas que deux lancements seront identiques : `random.seed()` sans argument réinitialise le hasard avant les phases.

Chaque CSV contient 10001 lignes et 18 colonnes. Les figures du script ont été construites avec un moteur graphique sans écran. L'interactivité de Spyder et une interface Windows ne sont donc pas validées ici. L'appel `report()` est commenté dans le simulateur : le rapport texte n'est pas automatiquement exécuté.

### Anomalies temporelles observées dans les deux exécutions

| Ligne de données précédente → suivante | Temps précédent → suivant (ms) | Constat |
| --- | --- | --- |
| 1007 → 1008 | 1006 → 1006 | doublon |
| 4986 → 4987 | 4984 → 4986 | saut de 2 ms |
| 9816 → 9817 | 9815 → 9815 | doublon |

Le pas observé vaut 1 ms pour 9997 intervalles, 0 ms pour deux intervalles et 2 ms pour un intervalle. La dernière valeur est 9999 ms. Le temps de simulation est incrémenté avec des flottants, puis le logger applique `int(t*1000)` : cette troncature produit ces anomalies. Une reproduction isolée du calcul confirme les mêmes valeurs. Cela ne démontre pas une perte de mesure physique.

Conséquence pour VISU : détecter et montrer les anomalies, conserver chaque ligne et son temps d'origine. Ne pas dédupliquer, trier ou rééchantillonner automatiquement. Une correction du générateur devrait être séparée, documentée et discutée avant utilisation comme référence temporelle.

### Autres points à connaître

- L'appel explicite du générateur de rapport échoue dans les deux cas avec `KeyError: 'ov_p1'`. Il attend `ov_p1`, `ov_p2`, `ov_p3`, `ov_c1`, `ov_c2`, `ov_pub`, absents du CSV. Ne pas inventer ces mesures en les remplissant de zéros.
- `failure_plc` reste à 0, tandis que le consommateur 1 passe bien à `FAILED` et le 2 à `ACTIVE`. L'affectation de `failure_plc` est locale à la fonction imbriquée `work_phase` : la déclaration `global` de la fonction englobante ne s'y applique pas. Ce marqueur n'est donc pas une référence fiable pour dater la panne dans cette version.
- Les cellules vides initiales de `pub_output` correspondent à l'absence de publication au démarrage. Les remplacer par zéro changerait leur sens.
- `pub_output` conserve ensuite la dernière valeur publiée à chaque ligne du logger. Une cellule non vide ne signifie donc pas « nouvelle publication ». Exécution 1 : 999 événements de publication, mais 9985 lignes non vides. Exécution 2 : 981 événements, mais 9806 lignes non vides. Le calcul de reprise du rapport basé sur `.notna()` est à revoir avant d'être pris comme référence.
- Le logger est exécuté avant le traitement des événements en attente de cette itération. Les instants observés sur les courbes incluent cette convention d'enregistrement. Ne pas confondre instant planifié, instant de traitement et instant de journalisation.
- Les trois producteurs tournent à 10 ms et les deux consommateurs à 20 ms, avec déphasages/jitters, mais tous sont enregistrés sur la même colonne `t_ms`. Diviser les colonnes en cinq fichiers teste l'import multi-fichiers, pas cinq horloges indépendantes. Ne pas inventer une correction de décalage qui effacerait un vrai retard de transmission.

## 3. Dépendances et environnement

| Composant | Bibliothèques externes directement utilisées/importées |
| --- | --- |
| Diagnostic VISU et lanceur guidé | Aucune, bibliothèque standard Python seulement |
| Redundancy10.py | NumPy et SciPy, plus les deux modules locaux |
| graphical_report10.py | pandas et Matplotlib |

Essai réalisé : Linux, interpréteur 64 bits, Python 3.12.14. Versions observées : NumPy 2.3.5, SciPy 1.17.0, pandas 2.2.3, Matplotlib 3.10.8. Ces versions ne constituent pas un fichier d'installation compatible Python 3.11 et ne doivent pas être recopiées aveuglément comme contraintes.

La validation Windows 11 / Python 3.11 doit être faite sur le poste cible, avec relevé des versions installées et, ultérieurement, des dépendances transitives, licences et contraintes d'installation. Aucune bibliothèque du simulateur n'est automatiquement une dépendance de l'application VISU.
